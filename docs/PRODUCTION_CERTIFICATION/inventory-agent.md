# Inventory, warehouse lifecycle and financial integrity audit

Audit date: 26 October 2026. Scope: the current, already modified Next.js working tree. Existing changes were preserved. Business-logic certification: **FAIL / NO-GO**. Passing tests below prove that defects are reproducible; they do not mean the affected business processes pass acceptance. Inventory accounting and financial rules were not changed because the requested workflow reserves those changes for user approval.

## Safety and evidence

- No production database, external network service, deployed API or existing seed/acceptance script was used for this audit.
- Mock-only evidence: `lib/inventory/production-audit-reproductions.test.ts` (4/4 passed) and `lib/auth/inventory-route-access.test.ts` (9/9 passed). Command: `vitest run lib/auth/inventory-route-access.test.ts lib/inventory/production-audit-reproductions.test.ts --maxWorkers=1`.
- Real database evidence: `scripts/audit-transfer.integration.ts`, invoked only by `vitest run --config vitest.audit.config.ts --disableConsoleIntercept` (4/4 passed). A cached MongoDB 8.2.6 executable starts a new single-member loopback replica. Prisma receives an explicit random `benaa_audit_<timestamp>` database URL, validated against `127.0.0.1`, without importing `prisma/client` or loading `.env`. Production credentials are never used. Downloads are disabled. The verified super-admin session and cache invalidation are mocked (cache network effects prohibited); Prisma, MongoDB transactions and route handlers are real. Five warehouses are created dynamically. Cleanup disconnects Prisma and stops the disposable replica.
- Sandbox temp-cache renames initially failed with EPERM; redirecting TEMP/TMP to workspace `.audit-temp` resolved mock runs. Loopback access initially failed EACCES; approved elevated execution enabled the disposable replica. These were environment restrictions, not application results.
- `isolated-contention-metrics.json` contains complete observed metrics and five-warehouse discovery response. These are local contention observations with direct route calls, no deployed HTTP stack, no production indexes/replication topology or real authentication. They are not a production throughput, sustained soak or high-load certification.

## Blocking defects and reviewable patch recommendations

| ID | Severity | Evidence and impact | Recommended correction (approval required) |
|---|---|---|---|
| INV-01 | Critical | `app/api/inventory/transfers/lifecycle/route.ts:439` accepts RECEIVE from APPROVED. Real sequence REQUEST 30 -> APPROVE -> RECEIVE 30, with no dispatch, changed warehouse total **500 -> 530**, left source stock **100** and reservation **30**. | Permit receipt only after dispatch; represent in-transit ownership explicitly and reconcile product, warehouse, bin and movement quantities in one transaction. |
| INV-02 | Critical | Same route `:449` parses unchecked receivedQuantity and adds it at `:458`. Real receipt **-150** changed destination **100 -> -50**, returned HTTP 200 and completed the transfer. Over-receipt is also not bounded. | Require finite numeric receipt quantities, enforce approved quantity/remaining amount, and define an approved discrepancy workflow. Reject invalid receipts before any write. |
| INV-03 | Critical | Same route `:347` and `:439` check status before entering transactions, then use the previously read transfer. Controlled interleaving of two real requests that both passed APPROVED before transaction entry allowed **two 10-unit dispatches for one 10-unit transfer**, source **100 -> 80**, two ledger rows, both HTTP 200. | Claim the expected transfer state with conditional update inside the same transaction as stock and ledger writes; enforce an operation idempotency key and bounded transaction-conflict retries. A status check outside the transaction cannot provide replay protection. |
| INV-04 | High | `lib/procurement/procurementService.ts:332` commits GRN POSTED before validating PO or processing stock. Each `executeStockMutation` at `:371` opens its own transaction; later PO, batch and audit changes are separate writes. Mocked real-service call against cancelled PO throws while receipt remains POSTED; no outer transaction was invoked. | Place conditional state claim, current PO validation, all receipt lines, batch stock, PO totals and audit in one transaction; validate every line before applying mutations. Add late-line failure/rollback and simultaneous separate GRN tests. |
| INV-05 | High | `lib/dispatch/dispatchService.ts:221` marks current dispatch POSTED, `:411` selects all POSTED dispatches, and `:417`/`:420` adds current items and queried items again. Mocked service completes a 100-unit order after dispatching **50**. | Sum the current dispatch once; reconcile by salesOrderItemId rather than productId, and derive fulfilled quantity from authoritative posted documents. |
| INV-06 | High | Dispatch deductions occur only inside the binAllocations loop (`lib/dispatch/dispatchService.ts:303`), with no assertion that allocation totals equal item dispatchedQuantity. A mocked 50-unit dispatch with empty bins posted and completed without any stock-service deduction. | Require at least one valid bin allocation for positive dispatched quantities and equality of allocation/item totals after conversion; reject incomplete pick/dispatch snapshots. |
| INV-07 | High | `lib/reservations/reservationService.ts:149` checks each order line against existing DB reservations, but only inserts all new lines after checks (`:179`). Two same-product lines of 60 each reserve **120 against stock 100** in the mocked service. | Aggregate requirements by warehouse/product/base unit before availability validation and atomically claim available stock. Keep line identities for fulfillment. |
| INV-08 | High | Transfer reservations use StockAllocation.reservedQuantity (`lifecycle:237`); sales reservations use StockReservationItem totals, and `getAvailableStock` omits the allocation reservation field. Central outbound stock service validates physical balances but does not enforce these commitments. | Define one authoritative reservation model covering transfer and sales commitments, derive one availability figure, and enforce it consistently across all outbound operations. Review existing legacy `Order` commitments as well. |
| INV-09 | High | Lifecycle dispatch updates only source warehouse quantity (`:373`), receipt only destination (`:477`); neither uses central stock service, bins, base-unit conversion or Product.quantity. TRANSFER_OUT ledger quantities are negative (`:385`), unlike central service positive movement magnitude plus direction. Discrepancy rows record nonzero quantity with unchanged previous/new stock (`:505` onward). | Approve a ledger convention and in-transit/variance policy; centralize mutation logic while keeping transfer global conservation and product/bin totals consistent. Add reconciliation invariants for every transition. |
| INV-10 | High | Unit conversion (`lib/units/unitService.ts:109`) silently returns unchanged quantity for unknown conversions. Sales reservation compares ordered units directly to physical base stock. Dispatch warehouse/bin prechecks compare unconverted quantities before central conversion. | Reject missing/incompatible conversion; normalize commitments, receipt limits, picks and dispatch totals to base units, retaining transaction-unit snapshots for display. |
| FIN-01 | High | `lib/payments/order-payment-from-amounts.ts:147` sets paid when fullyPaid before the cancelled-state guard. Mocked helper: cancelled invoice + full 100 payment => **paid**. | Preserve cancelled state before all settlement promotion, define late processor-event policy and validate duplicate event/refund behavior. |
| FIN-02 | High | `lib/payments/order-payment-from-amounts.ts:83` confirms the order before stock fulfillment at `:95`; fulfillment errors are caught/logged (`:104`) and returned as success. Retry sees order already confirmed and skips the first-payment fulfillment path. | Atomically record money/order/stock where possible, or use an idempotent outbox/reconciliation operation with explicit failure status and retry; never permanently swallow stock-fulfillment failure. |

Additional static gaps (not independently reproduced): reservation release permits release beyond remaining quantity (`reservationService:263`), cancellation does not release batch reservations (`:349` onward); fulfillment matches the first dispatch item by product (`dispatchService:358`) rather than order-line identity; createDispatch omits batch identifiers from copied item/bin snapshots while postDispatch deducts batch only for item.batchId (`:317`); bin relocation reads source balance before its transaction (`stockService:425` -> `:440`). Concurrent reservation creation reads other reservations but writes separate reservation documents, so transaction snapshot isolation alone does not establish exclusive capacity claims. These require isolated race/rollback tests before acceptance.

## Lifecycle assessment

| Process | Implemented path | Assessment |
|---|---|---|
| Direct warehouse transfer | Central paired TRANSFER_OUT/IN transaction plus completed transfer | Static atomic grouping exists; unit, commitment and concurrent conflict behavior still need tests. |
| Lifecycle transfer | REQUEST reserves allocation -> APPROVE -> DISPATCH deducts -> RECEIVE credits/completes; CANCEL releases before dispatch | Fails conserved quantity, positive receipt and concurrent replay invariants as proven above. No implemented IN_TRANSIT transition despite accepted state. Partial receipt immediately completes, with no remaining receipt document. |
| Procurement | DRAFT PO -> PENDING_APPROVAL -> APPROVED -> DRAFT GRN -> POSTED and partial/full PO | GRN atomicity fails. Mixed units and separate receipts competing for remaining quantities need verified tests. |
| Sales fulfillment | DRAFT -> PENDING_APPROVAL -> APPROVED -> reservation -> pick -> completed pick -> DRAFT dispatch -> POSTED | Duplicate-line reservation and dispatch completion fail; batch and allocation totals have gaps. |
| Legacy commerce | Order/reserved quantity -> invoice payment synchronization -> fulfillment | Runs alongside SalesOrder workflow with different commitment and fulfillment semantics; no unified accounting certification possible from current evidence. |
| Mobile sync | Direct global product quantity updates and movement snapshots | Administrator containment added; writes still bypass warehouse/bin/ledger reconciliation. The record_movement payload uses fields absent from current StockMovement schema and cannot be accepted as accounting-grade sync. No accounting repair made. |

## Contention observations

Each cell below shows successes/errors then p95 latency in milliseconds. All clients target the same product/allocation. REQUEST calls are independent one-unit requests; DISPATCH and RECEIVE calls contend on one transfer. Failed responses exposed raw Prisma write-conflict messages as HTTP 400. The single-member test is deliberately narrow.

| Clients | REQUEST | DISPATCH | RECEIVE |
|---|---|---|---|
| 10 | 1/9, 45 ms | 1/9, 47 ms | 1/9, 46 ms |
| 25 | 1/24, 85 ms | 1/24, 104 ms | 1/24, 76 ms |
| 50 | 1/49, 132 ms | 1/49, 119 ms | 1/49, 131 ms |
| 100 | 1/99, 248 ms | 1/99, 248 ms | 1/99, 265 ms |

Sequential retry after each successful DISPATCH/RECEIVE batch returned 400 with no extra quantity change. This proves only sequential rejection; controlled stale concurrent prechecks separately proved duplicate dispatch. Cross-warehouse lookup returned all five dynamically created warehouses, including the deliberately corrupted negative balance. No capacity-independent or production latency claim follows from these observations.

## Safe changes made

`lib/auth/inventory-route-access.ts` and its tests protect the three new inventory/mobile endpoints with current verified sessions and permission checks. Transfer audit identity is overwritten from the server session; destination receipt, source dispatch and manager approval are checked against current assignments and roles. Transfer listings are scoped. Cross-warehouse discovery requires STOCK_VIEW and validates any asserted current warehouse; discovery across warehouses remains intentional for interwarehouse requests. The entire legacy global mobile endpoint now requires administrator authority; fake bcrypt strings were replaced with real hashing and password validation. Parent/security agents are separately reviewing broader scope and cache invalidation changes.
